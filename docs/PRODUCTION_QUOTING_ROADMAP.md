# 製造業報價全生命週期管理：單企業本機版路線圖

版本：1.0（2026-11-04）　｜　狀態：技術開發中，只用合成資料驗證

## 1. 已完成的功能
- 成本影響與客戶報價毛利風險（主頁）
- Excel 欄位對應
- 歷史報價匯入、相似案件與建議報價
- 報價工作台：批次成本、數量階梯、版本比較、客戶草稿
- 公開靜態網站與 Demo（`web/`；本階段不修改）

## 2. 尚缺少的商業工作流程
- 詢價（RFQ）案件的建立與追蹤
- 報價版本與成交結果的長期保存
- 實際成本回饋，以及預估與實際的差異分析
- 本機資料的備份與還原

## 3. 適合的第一批企業客戶（假設，待驗證）
- 有 1～3 位報價人員、使用 Excel 或 ERP 匯出資料的少量多樣製造業。
- 願意在**一台指定電腦**上保存報價紀錄，並由一位負責人管理備份。

## 4. 單企業本機版的產品邊界
- 一家企業、一台電腦、一個 SQLite 資料庫檔案。
- 資料保存預設**關閉**，必須由使用者明確啟用，並指定資料庫路徑。
- 只保存使用者確認過的案件、報價版本、結果與成本紀錄；**不保存**上傳的原始 Excel。
- 沒有登入與權限；「操作人」欄位只是人工填寫，**不是**經過身分驗證的電子簽核。

## 5. 本機資料保存與備份策略
- 使用 Python 標準函式庫 `sqlite3`，日誌模式為 DELETE（不使用 WAL），資料庫只能放在本機磁碟，不可放在網路共享磁碟。
- 金額以文字儲存 Decimal 值；空白（未知）以 NULL 儲存，與 0 嚴格區分。
- 備份使用 SQLite 的線上備份 API（`Connection.backup`），不直接複製正在寫入的檔案。
- 還原前檢查備份的完整性與資料結構版本，並要求明確確認；還原前會自動保留目前資料庫的備份。
- SQLite 檔案**沒有加密**；需要加密時，使用作業系統的磁碟加密（例如 BitLocker、FileVault）。
- 資料庫與備份檔已加入 `.gitignore`。

## 6. 多人使用的限制
- 不支援多人同時寫入同一個資料庫，也沒有使用者、角色、權限。
- 多人需要使用時，應各自使用唯讀的報告，或改用未來的伺服器版。

## 7. 商業計算風險
- 報價當時的成本必須以**快照**保存，不可事後用今天的 BOM 覆蓋。
- 實際成本不完整時，不輸出實際毛利率。
- 已彙總的實際總成本與明細成本不可重複加總。
- 報價數量、成交數量、生產數量不同時，不自行分攤成本；口徑不一致時阻擋。

## 11. 設計審查（四個視角）

| 視角 | 質疑 | 決定 | 最終界線 |
|---|---|---|---|
| 報價主管 | 希望系統自動保存所有操作，不用每次確認 | **駁回** | 保存預設關閉；只保存使用者明確確認的資料 |
| 報價主管 | 狀態欄位可以當成主管核准紀錄 | **駁回** | 沒有登入，只能標示「人工填寫」，不是電子簽核 |
| 報價主管 | 修改報價時直接覆蓋舊版即可 | **駁回** | 每次修改都產生新版本，並且必須填寫原因 |
| ERP／成本顧問 | 事後用最新 BOM 重算當時的報價成本 | **駁回** | 保存報價當時的成本快照，不可覆蓋 |
| ERP／成本顧問 | 實際總成本與明細一起輸入，系統加總 | **採納（防呆）** | 兩者擇一；同時提供時阻擋，避免重複計算 |
| ERP／成本顧問 | 成交數量與生產數量不同時，按比例分攤成本 | **駁回** | 口徑不一致時阻擋，不自行分攤 |
| 資料安全工程師 | SQLite 放在網路磁碟，讓多人共用 | **駁回** | 只放本機；不使用 WAL；文件寫明不支援多人寫入 |
| 資料安全工程師 | 直接複製 .db 檔案就是備份 | **駁回** | 使用線上備份 API；還原前檢查完整性與版本 |
| 資料安全工程師 | 為方便追查，保存原始 Excel | **駁回** | 不保存原始檔，只保存來源檔名與列號 |
| 客戶導入人員 | 客戶不知道資料庫要放哪裡 | **採納** | 路徑必須明確指定；文件說明建議位置與磁碟加密 |
| 客戶導入人員 | 備份還原太複雜 | **採納** | 介面提供備份與還原入口；還原需二次確認 |
| 客戶導入人員 | 新版程式會不會讓舊資料庫壞掉 | **採納** | 資料結構版本與升級程序；版本不相容時拒絕開啟 |

沒有阻擋級的規格矛盾。
